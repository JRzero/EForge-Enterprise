# 采购审批示例边界与验证

状态：实现中，最终本地/云端回归待收口。规格见 `spec/purchase-approval-sample.md`，证据索引见 `tasks/purchase-approval-sample.md`。

## 业务与权限

采购代码保留在workflow模块的purchase包，业务接口位于workflow-api；不抽象成通用订单系统。金额、主子明细、附件和事件均由采购业务拥有；Flowable只负责既有白名单内的审批执行。

`sample:purchase:list`控制查询，`sample:purchase:write`控制草稿、附件、提交和撤回，`sample:purchase:approve`控制决定。新角色不会自动取得这些权限。控制器读取认证身份，服务再次检查有效账号、所有权和指定审批人。超级管理员仍不能查看其他人的采购数据；其通配功能权限不绕过业务参与者边界。草稿仅本人可读，提交后的指定审批人可读取。附件逐次鉴权，不提供匿名profile链接。

审批人选项来自当前有效用户、角色和菜单授权，排除本人。提交和审批再次核验当前资格。实际HTTP撤销角色后审批返回403；业务层对直接调用也检查当前审批角色。该行为沿用现有权限事务模型，未新增全局授权锁，也不宣称与任意并发撤权事务形成新的线性化协议。

## 金额与一致性

HTTP金额/数量/版本均使用字符串，前端不计算提交总额。服务端使用BigDecimal，逐行乘积HALF_UP到两位再合计，限制数量/单价/总额与明细数量，拒绝指数、NaN、超精度与重复行标识。

草稿创建唯一键为申请人+命令编号，后续命令唯一键为采购单+操作者+命令编号，另有每单版本唯一约束。相同内容重试返回已存在状态；同编号不同内容或过期版本拒绝。事务沿用WorkflowUnitOfWork，业务、引擎、事件一起提交或回滚。

真实MySQL首次并发创建测试揭示：插入前读取账号会建立旧RR快照，重复插入等待后仍看不到另一事务的完整记录。修复为先按创建键插入/锁定，再读取身份和内容；无效身份仍回滚未提交行。两大小写模式均已验证，不增加全局运行锁。

采购发布需实际批准和拒绝场景证明；绑定只有一个同步人工任务，受控`${approver}`由服务端填入，结束节点必须为approvedEnd/rejectedEnd。采购独立激活，不修改leave。审批完成后检查真实结束节点与实例终止，异常回滚。

## 附件与输出

最多5个附件、每个5MiB；文件名不接受路径和控制字符。PNG/JPEG按真实图片解析并限制像素数；PDF仅检查格式标记，不等同于恶意软件扫描或完整PDF结构验证。内容保存在该示例的私有关系表中，下载统一attachment、application/octet-stream、no-store、nosniff，页面不内嵌执行内容。未来如接入对象存储应保持这些访问边界，不直接暴露永久公共链接。

原始SQL、驱动异常和附件内容不写入操作请求审计。响应使用固定ProblemDetail错误；页面通过React文本节点呈现名称/意见，模拟浏览器已检查恶意标签文本保持惰性。

## 已知验收边界

本示例不处理付款、库存、供应商主数据、多级/会签、动态表单，也没有Agent采购写工具。原Flowable Agent配置能力与采购业务命令不是同一能力。当前附件采用逐个确认上传，服务端版本序列化；不宣称支持断点续传、病毒扫描或大文件仓库。
