# 规范 API 故障排查

用户错误响应中的 `requestId` 与 `X-Request-ID` 是同一个服务端编号。取得编号和大致发生时间后，在对应应用实例日志中精确搜索编号，定位 `api_server_error` JSON事件。

1. 核对 `status`、`code` 和 `errors[].locations`。500及其他非503的5xx为ERROR，503为WARN；功能未启用与依赖暂不可用由安全错误码区分。4xx只有关联编号，通常不会产生服务器故障记录。
2. 根据异常类型和应用位置检查相应数据库、Redis或存储服务的健康状态。不要要求用户提供密码、JWT或完整请求体，也不要为了排查开启SQL/请求体全量日志。
3. 生成器创建表或自定义输出的错误先检查返回的 `creation` / `output` 结果；部分DDL和文件不会自动回滚，禁止直接重试覆盖或删除已有数据。
4. 记录请求编号、状态、错误码、影响时间及修复验证。若日志无匹配，先确认实例/时间/日志保留范围，再检查是否属于4xx、历史兼容接口或不经过规范错误边界的失败。

日志只保留受控类型与有限代码位置，不含原始异常消息。需要更多证据时在隔离环境复现，保持数据脱敏。按固定event/status/code统计次数即可识别重复故障；不要以高基数requestId建立监控指标序列。
