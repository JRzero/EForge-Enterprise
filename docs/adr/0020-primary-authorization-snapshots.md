# ADR 0020：受保护请求以主库一致快照核验权限

日期：2026-10-15。决策已采用，最终交付验收仍由 `tasks/framework-hardening.md` 的 H01/H13 记录。

## 问题

原角色/菜单写入提交 SQL 后刷新 Redis 会话。真实故障已证明：Redis KEYS 失败会阻止刷新，但授权删除已经提交；恢复 Redis 后，两份旧 JWT 仍能使用缓存中的权限。只在 bootstrap 或登录时刷新不能封闭这条路径，单个会话刷新失败也不能成为其他会话继续保留权限的理由。

## 决策

1. Redis 只证明会话存在及其剩余有效期。JWT 过滤器在安装受保护请求的身份前，必须通过 `AuthorizationSnapshotService` 从 MASTER 读取当前用户、有效角色、各角色权限及数据范围，再执行原授权逻辑。缓存授权字段不作为放行依据。
2. 读取使用独立短 `REQUIRES_NEW`、readOnly、REPEATABLE_READ 事务。先选主库再取连接；恢复调用方数据源和事务上下文。角色、部门、权限属于同一数据库视图，提交失败时不部分更新请求对象。
3. bootstrap 的导航投影使用同一快照；SQL 读取完成后才写 Redis 或读取密码策略。控制台路径复用同一主库规则，并保留原 ticket、退出与 TTL 限制。旧 getInfo 投影已经核验的请求身份，避免重新拼接不同时刻的角色和权限。
4. 登录保留 Spring 原密码与锁定校验，只在创建会话前额外核对主库中的用户身份、账号名和已经验证过的密码 hash。这个最终读取是登录凭据核验点，不重新尝试密码、不增加错误计数。原有已登录会话不会仅因改密而新增强退行为。
5. SQL/会话存储不可用时安全拒绝，返回固定错误及诊断编号，不退回旧权限。退出只定位和删除 Redis 会话，不依赖 SQL；删除失败不能报告退出成功。
6. 保留原 bytes CAS、TTL-only 续期和不重建缺失 key。角色/菜单的 REQUIRED 参与事务在外层真正提交后才发布会话刷新；回滚不刷新。现有 mutation 锁和会话刷新行为暂不移除，规模优化由 H10 单独测量和验证。

## 语义边界

- 权限核验保证从该请求主库读取时刻起的快照一致性，不中断已经通过核验的在途操作，也不承诺 Redis 缓存投影每一瞬间都是最新。
- 用户禁用后成功删除的 key 不会因重新启用而复活。Redis DEL 失败返回503；未实现“禁用→启用”期间覆盖所有存储故障的持久账号代际协议。
- SQL 提交后刷新失败仍可能使修改请求返回错误；这不意味着 SQL 回滚，调用方应重新查询状态。已提交导入行的结果保持真实。
- afterCommit 验证针对现有 HTTP/REQUIRED 调用。未将它宣称为任意嵌套 savepoint 或 callback 内再次注册的通用事务协议。
- 此决策不增加全局 revision 表。版本快路径需要覆盖所有规范、兼容和直接数据库写入，否则会留下遗漏入口；以后只有实际成本证明必要且完整失效协议有证据时再评估。

## 成本及验证

原生 MySQL 122项断言证明主/从选择、调用方事务挂起恢复、并发修改下完整快照、最终凭据复核及故障恢复。独立 mutation probe 的6场景54项断言证明真实角色/菜单 SQL 提交、回滚、独立连接取锁和回调时机；该探针不宣称验证 Redis 实写。

当前权限读取的 mapper 查询数随角色数增长：2角色4条、5角色7条。带额外事务校验SQL的本机探针20次样本分别中位24.502/29.698ms、p95 35.377/33.004ms；这不是生产吞吐或纯请求开销测量，H10需进一步处理N+1和预算。

调用方已经持有连接时，REQUIRES_NEW 需要另一条可用连接。实际 maxActive=1 的外层事务场景约706ms后安全503，外层连接和事务恢复；maxActive=2能正常验证。生产连接池必须结合并发和内层事务预算配置，不能把增加池大小当作已验证的无限并发方案。

完整 MySQL/Redis 多会话故障矩阵、两配置浏览器、生成应用、OpenAPI和精确云端以安全审查与任务清单的最终证据为准。本 ADR 不是完整目标完成声明。
